# Agentflow Review: AI-Authored, Human-Corrected Syntax

## Executive Summary

Agentflow should not optimize for humans writing large diagrams from scratch.

It should optimize for:

1. AI generation correctness
2. human review and correction
3. deterministic validation
4. stable round-tripping
5. low ambiguity in semantic edits

This changes the design target.

The syntax can be verbose. The `agentflow: { ... }` wrapper is defensible. Strict metadata placement is defensible. Types, connectors, validation, and canonical formatting are defensible.

But ambiguity becomes less acceptable, not more. If humans are correcting AI output, they need to know exactly what a change means.

The current v0.7.0 draft is overcomplicated in the wrong places: too many overlapping concepts, overloaded association semantics, hidden semantic meaning in visual shapes, and unresolved core validation behavior.

The main decision:

> Agentflow should be framed as a canonical intermediate authoring format generated by AI, reviewed by humans, and consumed by tools — not as a friendly handwritten diagram language.

---

## Recommended Product Framing

Add this near the introduction of the spec:

```md
## Authoring Model

Agentflow is optimized for AI-assisted authoring with human correction.
The canonical syntax favors explicitness, deterministic validation, and stable
round-tripping over minimal keystrokes.

Humans are expected to read, review, and locally edit diagrams, but not usually
to write large Agentflow diagrams from scratch. Implementations SHOULD provide
autocomplete, validation, formatting, and AI repair workflows.
```

This resolves many syntax debates. Verbosity is acceptable if it buys validation, round-tripping, and repairability.

---

## Revised Success Condition

Use this as the v1 bar:

> In twelve months, an AI can generate a valid Agentflow diagram for a non-trivial agent workflow, and a human can review and correct it without reading the full spec.

If a human must constantly consult the spec to safely correct AI output, the syntax failed.

---

## What Is Acceptable Under This Authoring Model

These are acceptable because AI can emit them and validators can check them:

- verbose `agentflow: { ... }` metadata wrapper
- explicit metadata blocks
- YAML mappings for `params`
- strict namespace rules
- conformance fixtures
- capability checks
- types
- connectors
- validation tiers
- canonical-only forms before v1.0
- limited backward compatibility during draft phase

Do not optimize these away just to reduce keystrokes.

---

## What Remains Bad

These are still problematic because they make human correction unsafe:

- semantic meaning hidden in visual `shape`
- overloaded `---` association edge
- too many near-synonymous containers
- unclear executable vs descriptive posture
- broad instance binding and inheritance complexity
- open semantic questions in the spec
- historical migration clutter in the main authoring document
- unclear distinction between `description`, `prompt`, and `rule`

---

## Critical Issue 1: Stop Calling `shape` Presentation-Only

### Problem

The spec says Mermaid presentation keys at the top level of `@{...}` do not carry Agentflow semantics.

But `shape` clearly does carry Agentflow semantics:

- `shape: subroutine` makes a node a tool
- `shape: lean-right` makes a node an input
- `shape: procs` makes a node an external-file reference
- instance shapes determine binding type
- directive shapes affect semantic interpretation

This is a direct contradiction.

### Required Fix

Replace the current framing with:

```md
The `shape` key is a Mermaid rendering key with Agentflow semantic
interpretation for the shapes listed in §4.3. Other presentation keys remain
non-semantic unless explicitly specified.
```

### Decision Needed

Choose one:

1. Admit `shape` is semantic in Agentflow.
2. Introduce explicit semantic kind fields or keywords.

Do not keep saying `shape` is presentation-only while using it as a semantic discriminator.

---

## Critical Issue 2: Keep `agentflow: { ... }`, But Canonicalize Formatting

### Judgment

For AI-authored canonical syntax, the wrapper is fine. It creates a clean namespace and helps validators.

The issue is not the wrapper itself. The issue is inconsistent readability.

### Required Fix

Define canonical formatting rules:

- presentation keys first
- `agentflow` last
- stable key ordering inside `agentflow`
- one metadata block per element where possible
- formatter should preserve semantic comments only if intentionally supported

Recommended key order for tools:

```text
shape
agentflow.description
agentflow.connectorRef
agentflow.params
agentflow.returns
agentflow.output
agentflow.requires
agentflow.deny
agentflow.retry
agentflow.cache
agentflow.validate
agentflow.handler
agentflow.transport
agentflow.command
```

Example canonical form:

```text
search_web@{
  shape: subroutine,
  agentflow: {
    description: "Search the web for relevant sources",
    connectorRef: "web.search",
    params: { query: String, top_k: Int? },
    returns: "SearchResults",
    requires: ["net.read"]
  }
}
```

### Why It Matters

Human correction depends on predictable structure. If the AI emits fields in arbitrary order, review becomes slow and error-prone.

## Critical Issue 3: Reduce `---` Ambiguity

### Problem

`---` currently means:

- directive attachment
- reference document attachment
- taxonomy / classification
- general semantic association

Endpoint kind disambiguates the meaning.

That is elegant for a parser, but weak for human review. A human must inspect both endpoints and their shapes before understanding the relationship.

### Recommended Fix

Keep `---` as the canonical association operator, but prefer labels for AI output:

```text
search_web ---|directive| no_pii
write_copy ---|ref| brand_guide
net_read ---|taxonomy| net
```

Suggested rule:

```md
Association edges MAY be unlabeled when endpoint kind gives an unambiguous
interpretation. AI-authored canonical output SHOULD label association edges
with one of: `directive`, `ref`, `taxonomy`, or another implementation-defined
association kind.
```

### Why It Matters

Humans correcting AI output should not have to infer edge meaning from endpoint kind every time.

## Critical Issue 4: Clarify or Remove `skill`

### Problem

`flow`, `task`, and `skill` overlap semantically.

Current distinction:

- `flow`: sequence of steps
- `task`: discrete unit of work
- `skill`: composed capability with strategy

This is plausible in prose but fragile in real diagrams. Authors and AI systems will use them inconsistently.

### Option A: Keep `skill`, But Define Hard Semantics

If retained, define it sharply:

- `flow`: executable sequence with data/control edges
- `task`: bounded execution scope inside an agent
- `skill`: reusable capability package, not directly executed unless invoked

Then validators should enforce that distinction.

### Option B: Remove `skill` From v1 Core

Simpler v1 core:

- `agent`
- `flow`
- `task`
- `directive`
- `testCase`

A skill can initially be modeled as a flow with metadata:

```text
some_capability@{
  agentflow: {
    kind: "skill",
    strategy: "parallel"
  }
}
```

### Recommendation

Remove or demote `skill` unless validation can enforce its distinction from `flow`.

## Critical Issue 5: Make Connectors First-Class or Admit the Compatibility Hack

### Problem

The current design says there is no `connector` keyword, but requires a magic top-level subgraph:

```text
subgraph connectors["Connectors"]
  github["GitHub"]
end
```

This is a keyword disguised as a subgraph convention.

### Better Syntax If Grammar Allows

```text
connector github["GitHub"]
github@{
  agentflow: {
    protocol: "http",
    endpoint: "https://api.github.com",
    token_required: true
  }
}
```

### If Mermaid Grammar Prevents This

Say so explicitly:

```md
Connector declarations use a required top-level `subgraph connectors[...]`
for Mermaid compatibility. Semantically, this subgraph is treated as the
connector registry.
```

### Recommendation

Either:

1. introduce a real `connector` declaration, or
2. explicitly document the current form as a Mermaid compatibility encoding.

Do not pretend the current form is conceptually simpler.

---

## Critical Issue 6: Defer Broad Instance Binding

### Problem

The current instance system includes:

- agent instances
- flow instances
- skill instances
- tool instances
- directive instances
- inheritance
- overrides
- cyclic binding errors
- kind matching
- open cardinality questions
- directive-instance ambiguity

That is too much machinery for v1 unless strong use cases prove it is necessary.

### Recommendation

For v1, keep only what is essential.

Preferred option:

- keep tool invocation/reference mechanics
- defer agent/flow/skill/directive instance inheritance

Alternative:

- keep only `win-pane` tool instances
- defer `tag-rect`, `delay`, `lin-rect`, and `curv-trap`

### Why It Matters

AI can generate instance bindings, but humans correcting them will make mistakes. Inheritance and local overrides are especially easy to misunderstand.

## Critical Issue 7: Treat Diagnostics as Product UX

### Problem

For AI-authored, human-corrected syntax, diagnostics are not just implementation detail. They are the repair interface.

Bad diagnostic:

```text
Invalid metadata applicability.
```

Good diagnostic:

```text
`requires` is valid on tools only. Move it under the tool node's `agentflow`
block, or use `permits` on the enclosing agent.
```

### Required Fix

Add repair-oriented conformance fixtures.

Fixtures should cover:

- wrong edge label into multi-param tool
- domain key accidentally placed at top level
- connectorRef typo
- connectorRef pointing outside connector registry
- wrong shape for intended element
- directive attached with wrong edge
- `description` used where `prompt` is likely intended
- `rule` missing on directive
- `requires` not covered by nearest agent `permits`
- tool invocation outside an enclosing agent
- duplicate IDs
- unresolved type/template reference

### Recommendation

Create a separate diagnostics/conformance spec if needed, but do not leave repair quality to implementations.

---

## Critical Issue 8: Separate Current Syntax From Changelog

### Problem

The spec currently starts with long historical sections. That is useful for implementers tracking churn, but hostile to users evaluating the current language.

### Required Fix

Split into:

1. `agentflow-syntax.md` — current authoring syntax only
2. `agentflow-changelog.md` — version deltas and governance
3. `agentflow-conformance.md` — validation and diagnostic expectations

### Recommended Opening Structure

The syntax spec should start with:

1. one-paragraph purpose
2. authoring model
3. smallest useful example
4. core concepts
5. syntax reference
6. advanced semantics

Do not begin with archaeology.

## Recommended Layering

Use three layers.

### Layer 1: Canonical Agentflow

The verbose syntax AI emits and validators consume.

Properties:

- explicit
- deterministic
- stable formatting
- minimal equivalent forms
- strict metadata placement

### Layer 2: Human Review Format

Same syntax, but formatted predictably for correction.

Properties:

- stable key order
- readable grouping
- useful comments if supported
- repair diagnostics from validator/editor

### Layer 3: Semantic Model

Internal AST / export / runtime interpretation.

Properties:

- namespace resolution
- capability evaluation
- connector binding
- type/template resolution
- validation tiers
- conformance output

### Important

Do not create many syntactic aliases. AI will use them inconsistently and humans will suffer.

---

## Recommended v1 Core Concepts

Keep the author-facing model small:

1. Actor: `agent`
2. Work: `task` / `flow`
3. Capability: tool node with `shape: subroutine`
4. Information: data nodes plus `type`
5. Constraint: `directive`
6. Boundary: connector registry

Everything else should be advanced mode or deferred.

---

## Recommended Cuts or Deferrals Before v1

### Cut or defer

1. Broad instance binding for agents/flows/skills/directives
2. `skill` as a first-class primitive unless strongly validated
3. separate `template` concept unless runtime need is proven
4. unlabeled overloaded `---` in AI canonical output
5. historical changelog sections in the main syntax spec
6. claim that `shape` is presentation-only
7. unresolved connectorRef validation wording
8. unresolved instance-binding cardinality

### Keep

1. `agent`, `flow`, `task`
2. tool definitions via `shape: subroutine`, if `shape` is admitted as semantic
3. `params` / `returns`
4. `permits` / `requires`
5. `prompt` on agents
6. `directive.rule`
7. connector binding, but with clearer declaration semantics
8. YAML mapping for params
9. `agentflow: { ... }` wrapper
10. strict validation and conformance fixtures

## Bottom Line

Your clarification saves the verbose canonical style.

It does not save the whole spec.

If AI authors and humans correct, Agentflow can be explicit and somewhat verbose. But it must be brutally consistent.

Humans should never have to ask:

- Is this shape semantic or visual?
- Which meaning of `---` is this?
- Is this a flow or a skill?
- Why is connector a subgraph but not a keyword?
- Does this instance inherit behavior or just display metadata?

Fix those, and the complexity becomes tolerable.

Leave them, and AI will generate diagrams that look valid while humans cannot safely correct them.
